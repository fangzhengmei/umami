# 转化统计核心代码深度分析

## 一、Session 去重计数机制

### 1.1 核心 SQL 结构

目标转化统计使用 **会话级别的去重计数**，核心 SQL 结构如下 (`src/queries/sql/reports/getGoal.ts:55-76`)：

```sql
-- PostgreSQL 版本
select 
  count(distinct website_event.session_id) as num,    -- 转化数：去重的会话数
  (
    select count(distinct website_event.session_id)
    from website_event
    where website_event.website_id = {{websiteId::uuid}}
      ${dateQuery}
      ${excludeEventTypeFilterQuery}
  ) as total  -- 总访客数：时间范围内的所有会话
from website_event
where website_event.website_id = {{websiteId::uuid}}
  and ${column} ${operator} {{value}}    -- 目标匹配条件
  ${dateQuery}
  ${filterQuery}
```

### 1.2 关键概念区分

| 指标 | 含义 | SQL 实现 |
|------|------|----------|
| **num** | 完成目标的独立访客数 | `count(distinct session_id)` + 目标条件 |
| **total** | 时间范围内的总独立访客数 | `count(distinct session_id)` + 仅日期条件 |
| **转化率** | 目标完成比例 | `num / total` |

### 1.3 去重计数的意义

使用 `count(distinct session_id)` 而不是 `count(*)` 的原因：

1. **访客级统计**：统计的是"多少个用户完成了目标"，而不是"目标被触发了多少次"
2. **避免重复计数**：一个用户（session）多次触发同一目标，只计一次转化
3. **业务意义**：转化率通常用于衡量访客的转化比例，而不是事件触发频率

**示例**：
```
访客A访问 /checkout/complete 3次
访客B访问 /checkout/complete 1次

count(*): 4次（事件命中数）
count(distinct session_id): 2人（转化数）
```

## 二、事件命中与转化计数的区分

### 2.1 两层统计逻辑

在 SQL 查询中，存在两层统计：

```
┌─────────────────────────────────────────────────────────────┐
│  外层查询：num = 转化数                                      │
│  count(distinct session_id)                                 │
│  WHERE 目标匹配条件 + 日期 + 所有过滤条件                    │
└─────────────────────────────────────────────────────────────┘
                            ↓
┌─────────────────────────────────────────────────────────────┐
│  子查询：total = 总访客数                                    │
│  count(distinct session_id)                                 │
│  WHERE 仅日期条件 + 排除 event_type 的过滤条件              │
└─────────────────────────────────────────────────────────────┘
```

### 2.2 代码中的关键处理

**关键点 1：`excludeEventTypeFilterQuery` 的作用** (`getGoal.ts:49-53`)

```typescript
const excludeEventTypeFilterQuery = filterQuery
  .split('\n')
  .filter(filter => !filter.includes('event_type'))
  .join('\n')
  .trim();
```

**为什么要排除 event_type？**

计算 `total`（总访客数）时：
- 需要保留浏览器、国家、来源等维度过滤
- 但不能限制 event_type，因为总访客应该包括所有类型的事件（页面浏览、自定义事件等）
- 如果不排除 event_type，path 目标的 total 会只统计 pageView 事件，丢失 customEvent 的访客

**关键点 2：事件命中 vs 转化计数**

| 概念 | 含义 | 对应代码 |
|------|------|----------|
| **事件命中 (Event Hit)** | 满足目标匹配条件的原始事件记录 | `WHERE url_path = '/checkout'` |
| **转化计数 (Conversion Count)** | 去重后的独立会话数 | `count(distinct session_id)` |

**注意**：事件命中数 ≥ 转化计数，因为一个会话可能多次触发同一目标。

## 三、event_type 过滤在 path/event 目标中的生效机制

### 3.1 目标类型与 event_type 的对应关系

根据目标类型，自动设置对应的 event_type 过滤 (`getGoal.ts:30,86`)：

```typescript
// path 类型目标 → 匹配页面浏览事件 (event_type = 1)
const eventType = type === 'path' ? EVENT_TYPE.pageView : EVENT_TYPE.customEvent;
```

**EVENT_TYPE 常量定义** (`src/lib/constants.ts:114-120`)：

```typescript
export const EVENT_TYPE = {
  pageView: 1,     // 页面浏览
  customEvent: 2,  // 自定义事件
  linkEvent: 3,    // 短链接点击
  pixelEvent: 4,   // 像素追踪
  performance: 5,  // 性能指标

```

### 3.2 event_type 过滤的完整链路

#### 步骤 1：传入 parseFilters

#### 步骤 2：FILTER_COLUMNS 映射

在 `src/lib/constants.ts:91`：

```typescript
export const FILTER_COLUMNS = {

  eventType: 'event_type',  // 前端参数名 → 数据库字段名

```

#### 步骤 3：filtersObjectToArray 解析

在 `src/lib/params.ts:42-76`：
```typescript
export function filtersObjectToArray(filters: QueryFilters, ...): Filter[] {
  return Object.keys(filters).reduce((arr, key) => {
    const baseName = key.replace(/\d+$/, '');
    // ...
    return arr.concat({
      name: baseName,                // 'eventType'
      column: FILTER_COLUMNS[baseName], // 'event_type'
      operator,
      value,
      // ...
    });
  }, []);
}
```

#### 步骤 4：getFilterQuery 特殊处理

**ClickHouse 版本** (`src/lib/clickhouse.ts:107-129`)：
```typescript
function getFilterQuery(filters: Record<string, any>, options: QueryOptions = {}) {
  // ...
  filtersObjectToArray(filters, options).forEach(({ name, column, operator, paramName }) => {
    if (column) {
      // eventType 被标记为 isAlwaysAnd，总是使用 AND 连接
      const isAlwaysAnd = name === 'eventType' || ...;
      
      if (isAlwaysAnd) {
        andClauses.push(
          // 注意：eventType 使用 UInt32 类型
          `and ${mapFilter(column, operator, name, name === 'eventType' ? 'UInt32' : 'String', paramName)}`,
        );
      }
      // ...
    }
  });
  // ...
}
```

**PostgreSQL 版本** (`src/lib/prisma.ts:108-150`)：
```typescript
function getFilterQuery(filters: Record<string, any>, options: QueryOptions = {}) {
  // ...
  filtersObjectToArray(filters, options).forEach(
    ({ name, column, operator, prefix = '', paramName }) => {
      if (column) {
        const clause = mapFilter(`${prefix}${column}`, operator, name, '', paramName);
        const isAlwaysAnd = name === 'eventType' || ...;
        
        if (isAlwaysAnd) {
          andClauses.push(`and ${clause}`);
        }
        // ...
      }
    },
  );
  // ...
}
```

#### 步骤 5：mapFilter 生成 SQL 条件

**ClickHouse 版本** (`src/lib/clickhouse.ts:73-99`)：
```typescript
function mapFilter(column: string, operator: string, name: string, type: string = 'String', paramName?: string) {
  const param = paramName ?? name;
  const value = `{${param}:${type}}`;  // eventType → {eventType:UInt32}

  switch (operator) {
    case OPERATORS.equals:
      return `${column} IN {${param}:Array(${type})}`;
    // ...
  }
}
```

**最终生成的 SQL 条件**：
```sql
-- path 类型目标
AND event_type IN {eventType:Array(UInt32)}  -- eventType = [1]

-- event 类型目标  
AND event_type IN {eventType:Array(UInt32)}  -- eventType = [2]
```

### 3.3 为什么 eventType 需要特殊处理？

1. **数据类型不同**：`event_type` 是数值字段 (UInt32/Integer)，其他大多数字段是字符串
2. **逻辑重要性**：目标类型（path/event）决定了基础事件类型，这个条件必须始终生效，不能被 OR 逻辑干扰
3. **参数传递**：`getQueryParams` 会将 eventType 转换为数组格式以匹配 `IN` 操作符

## 四、PRISMA/CLICKHOUSE 查询切换与 Kafka 写入链路界限

### 4.1 runQuery：查询层的数据库路由

**核心切换逻辑** (`src/lib/db.ts:22-36`)：

```typescript
export async function runQuery(queries: any) {
  // 优先级 1：如果配置了 CLICKHOUSE_URL
  if (process.env.CLICKHOUSE_URL) {
    // 检查是否有 Kafka 实现（注意：查询层通常没有 Kafka 选项）
    if (queries[KAFKA]) {
      return queries[KAFKA]();
    }
    // 使用 ClickHouse 查询
    return queries[CLICKHOUSE]();
  }

  // 优先级 2：检查 DATABASE_URL 类型
  const db = getDatabaseType();
  if (db === POSTGRESQL) {
    return queries[PRISMA]();  // 使用 PostgreSQL (Prisma)
  }
}
```

**查询层的数据库选择优先级**：
```
CLICKHOUSE_URL 已配置 → 使用 ClickHouse
    ↓
DATABASE_URL 是 postgres → 使用 PostgreSQL (Prisma)
    ↓
（其他数据库类型）
```

### 4.2 Kafka：仅用于写入链路

**Kafka 只在写入事件时使用**，查询层不经过 Kafka。

**写入链路代码** (`src/queries/sql/events/saveEvent.ts:259-263`)：

```typescript
async function clickhouseQuery({ ... }: SaveEventArgs) {
  const { insert, getUTCString } = clickhouse;
  const { sendMessage } = kafka;
  // ... 构造 message ...

  if (kafka.enabled) {
    // Kafka 启用时：发送到 Kafka 主题
    await sendMessage('event', message);
  } else {
    // Kafka 未启用时：直接写入 ClickHouse
    await insert('website_event', [message]);
  }
  // ...
}
```

**Kafka 启用条件** (`src/lib/kafka.ts:14`)：
```typescript
const enabled = Boolean(process.env.KAFKA_URL && process.env.KAFKA_BROKER);
```

### 4.3 完整架构：写入 vs 查询

```
┌─────────────────────────────────────────────────────────────────────────┐
│                            写入链路 (Ingress)                           │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│  POST /api/send                                                         │
│       ↓                                                                 │
│  saveEvent()                                                            │
│       ↓                                                                 │
│  runQuery({ PRISMA, CLICKHOUSE })  ← 根据配置选择                       │
│       │                                                                 │
│       ├─ PRISMA: 直接写入 PostgreSQL                                    │
│       │                                                                 │
│       └─ CLICKHOUSE:                                                    │
│              ↓                                                          │
│              kafka.enabled?                                             │
│                ├─ true → sendMessage('event', message) → Kafka 主题     │
│                │                         ↓                              │
│                │                     (消费者异步写入 ClickHouse)        │
│                │                                                        │
│                └─ false → insert('website_event', [message])           │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────────────┐
│                            查询链路 (Query)                             │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│  POST /api/reports/goal                                                 │
│       ↓                                                                 │
│  getGoal()                                                              │
│       ↓                                                                 │
│  runQuery({ PRISMA, CLICKHOUSE })  ← 注意：没有 KAFKA 选项！            │
│       │                                                                 │
│       ├─ CLICKHOUSE_URL 已配置 → clickhouseQuery() → 查 ClickHouse      │
│       │                                                                 │
│       └─ DATABASE_URL 是 postgres → relationalQuery() → 查 PostgreSQL   │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

### 4.4 关键界限总结

| 维度 | 写入链路 | 查询链路 |
|------|----------|----------|
| **Kafka 角色** | 可选的缓冲层（异步写入） | 不使用 |
| **ClickHouse 角色** | 最终存储（直接或通过 Kafka） | 查询引擎（优先选择） |
| **PostgreSQL 角色** | 备选存储（无 ClickHouse 时） | 备选查询引擎 |
| **切换触发** | Kafka 启用时自动切换到 Kafka | 根据 CLICKHOUSE_URL 环境变量 |
| **runQuery 选项** | 支持 KAFKA/CLICKHOUSE/PRISMA | 仅支持 CLICKHOUSE/PRISMA |

**注意**：查询层的 `getGoal`、`getFunnel` 等函数只提供 `PRISMA` 和 `CLICKHOUSE` 两个实现，**没有 KAFKA 实现**，因为 Kafka 不是查询数据库。

## 五、已修正的要点清单

### ✅ 修正 1：Session 去重计数的真正含义
- **之前理解**：可能以为是统计事件触发次数
- **正确理解**：使用 `count(distinct session_id)` 统计**独立访客数**，一个用户多次触发同一目标只计一次转化

### ✅ 修正 2：num vs total 的计算差异
- **之前理解**：可能以为只是多了一个目标条件
- **正确理解**：计算 `total` 时特意**排除了 event_type 过滤**，因为总访客数应该涵盖所有事件类型，而不是只统计目标类型的事件

### ✅ 修正 3：event_type 过滤的完整生效链路
- **之前理解**：可能以为只是简单的 where 条件
- **正确理解**：经过 5 个步骤（传入 → 映射 → 解析 → 特殊处理 → SQL 生成），且 eventType 在 ClickHouse 中使用 `UInt32` 类型，被标记为 `isAlwaysAnd` 确保始终生效

### ✅ 修正 4：path/event 目标与 event_type 的绑定关系
- **之前理解**：可能以为 path 目标只匹配 url_path，不限制事件类型
- **正确理解**：
  - `path` 类型目标 → `event_type = 1` (EVENT_TYPE.pageView) + `url_path` 匹配
  - `event` 类型目标 → `event_type = 2` (EVENT_TYPE.customEvent) + `event_name` 匹配

### ✅ 修正 5：Kafka 的角色与界限
- **之前理解**：可能以为 Kafka 是数据库选项之一，查询也会走 Kafka
- **正确理解**：Kafka **仅用于写入链路**，作为异步缓冲层；查询链路只在 ClickHouse 和 PostgreSQL 之间切换，不经过 Kafka

### ✅ 修正 6：runQuery 的真实选择逻辑
- **之前理解**：可能以为 Kafka > ClickHouse > PostgreSQL 是统一优先级
- **正确理解**：
  - 写入链路：Kafka（可选）→ ClickHouse / PostgreSQL
  - 查询链路：ClickHouse > PostgreSQL（没有 Kafka 选项）

### ✅ 修正 7：事件命中与转化计数的区别
- **之前理解**：可能将两者混为一谈
- **正确理解**：
  - **事件命中**：满足目标条件的原始事件记录数（count(*)）
  - **转化计数**：去重后的独立会话数（count(distinct session_id)）
  - 事件命中数 ≥ 转化计数

## 七、关键 SQL 示例

### PostgreSQL 目标查询示例（path 类型）
```sql
-- 目标：path = '/checkout/complete'
select 
  count(distinct website_event.session_id) as num,
  (
    select count(distinct website_event.session_id)
    from website_event
    where website_event.website_id = 'xxx'
      and website_event.created_at between '2024-01-01' and '2024-01-31'
      -- 注意：这里没有 event_type 限制！
  ) as total
from website_event
where website_event.website_id = 'xxx'
  and url_path = '/checkout/complete'        -- 目标匹配
  and event_type = ANY(ARRAY[1])            -- path 类型限制 pageView
  and website_event.created_at between '2024-01-01' and '2024-01-31'
```

### ClickHouse 目标查询示例（event 类型）
```sql
-- 目标：event = 'purchase'
select 
  count(distinct session_id) as num,
  (
    select count(distinct session_id)
    from website_event
    where website_id = 'xxx'
      and created_at between '2024-01-01' and '2024-01-31'
      -- 注意：这里没有 event_type 限制！
  ) as total
from website_event
where website_id = 'xxx'
  and event_name = 'purchase'              -- 目标匹配
  and event_type IN [2]                    -- event 类型限制 customEvent
  and created_at between '2024-01-01' and '2024-01-31'
```
